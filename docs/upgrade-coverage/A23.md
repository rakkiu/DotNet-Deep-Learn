## Vị trí yêu cầu chung và nội dung giữ lại

- [Bản chất và vai trò](https://client-ifz4.vercel.app/#/read/tasks-concurrency#identity): Concurrency là tổ chức nhiều công việc cùng có tiến triển; parallelism là thực thi thực sự cùng lúc. Thread là luồng thực thi của hệ điều hành; Task mô tả công việc/kết quả theo abstraction cao hơn. Async là cách không giữ thread chỉ để chờ I/O khi API hỗ trợ..
- [Nó giải quyết vấn đề gì?](https://client-ifz4.vercel.app/#/read/tasks-concurrency#problem): Một luồng UI bị chặn bởi tải file hoặc gọi mạng sẽ không phản hồi; server dùng một thread chờ mỗi request dễ cạn thread khi tải tăng. Tạo thủ công thêm thread cho mọi việc lại tốn bộ nhớ, context switch và công quản lý vòng đời..
- [Tại sao nên dùng nó?](https://client-ifz4.vercel.app/#/read/tasks-concurrency#benefits): API async cho phép chờ I/O mà không cần giữ một worker thread nhàn rỗi suốt thời gian chờ. ThreadPool/TPL hỗ trợ phân phối công việc CPU và ghép kết quả. Chọn cơ chế theo CPU-bound hay I/O-bound giúp giải quyết đúng nút thắt thay vì chỉ tăng số thread..
- [Giới hạn và điều kiện áp dụng](https://client-ifz4.vercel.app/#/read/tasks-concurrency#limits): Không dùng Task.Run để bọc mọi API I/O vốn đã có async. Không chạy nhiều việc CPU hơn mức tài nguyên cho phép rồi kỳ vọng nhanh hơn tuyến tính. Không dùng .Result/.Wait trên UI hoặc chuỗi gọi async nếu có thể await xuyên suốt..
- [Cơ chế hoạt động cốt lõi](https://client-ifz4.vercel.app/#/read/tasks-concurrency#mechanism): OS lập lịch thread lên CPU; nhiều thread hơn core phải chia thời gian. Thread trong process chia sẻ heap nhưng có call stack riêng. Một thao tác async bắt đầu chạy đồng bộ, có thể trả Task chưa hoàn tất khi cần chờ. Hoàn thành I/O sẽ kích hoạt phần tiếp tục theo runtime/context, không bảo đảm luôn là thread cũ hay luôn là thread mới..
- [Các khái niệm cốt lõi](https://client-ifz4.vercel.app/#/read/tasks-concurrency#concepts): Task, await, Concurrency và parallelism.
- [Tương tác với thành phần khác](https://client-ifz4.vercel.app/#/read/tasks-concurrency#integration): Web controller await EF Core/HttpClient; tác vụ CPU trên desktop có thể dùng Task.Run để giữ UI phản hồi. Shared state cần lock, semaphore hoặc thiết kế không chia sẻ. Cancellation là giao ước hợp tác xuyên API, không phải lệnh giết ngay công việc..

- [Cấu trúc thư mục & cấu hình](https://client-ifz4.vercel.app/#/read/tasks-concurrency#structure): Bố cục chính xác của từng ví dụ được liệt kê trong khối file của ví dụ đó. ## [Nền tảng junior cần giải thích được](https://client-ifz4.vercel.app/#/read/tasks-concurrency#junior)

Process có không gian tài nguyên của chương trình; thread là đường thực thi, ThreadPool tái dùng worker; Task đại diện hoàn tất/kết quả, không đồng nghĩa một thread ngủ. Async method có thể chạy đồng bộ trước điểm await chưa hoàn thành; WhenAll nhận các task, không tự start mọi tác vụ chưa được khởi chạy.

Chờ tuần tự: bắt đầu A, chờ A, bắt đầu B. Chờ chồng lấp: khởi tạo A/B độc lập rồi await tổng hợp. CPU parallel dùng nhiều core khi có tài nguyên. Timeline chỉ thể hiện quan hệ, không hứa tăng tốc vì scheduling, I/O và overhead khác nhau.

Bảng **Chọn theo nút thắt**: Nhu cầu / Công cụ cân nhắc / Giới hạn. Chờ network/file — API async + await — Không tự làm thiết bị nhanh hơn; CPU trên desktop — Task.Run/parallel có giới hạn — Đo overhead, giữ UI responsive; Shared state — lock/Interlocked/concurrent API — Không bảo vệ process khác; Giới hạn đang chạy — SemaphoreSlim — Không tự giới hạn backlog; Producer/consumer — Bounded Channel — Không bền vững sau crash.

Sơ đồ **I/O chồng lấp minh họa**: Bắt đầu A và B, mỗi API trả Task → Caller await WhenAll, không giữ worker chỉ để chờ I/O tự nhiên → B hoàn tất trước A vẫn là kết quả theo thứ tự input → Lỗi/hủy cần được quan sát; không suy thread ID.

## [Đào sâu middle và các đánh đổi](https://client-ifz4.vercel.app/#/read/tasks-concurrency#middle)

Race là phụ thuộc truy cập không đồng bộ; deadlock là vòng chờ; starvation là công việc không có đủ cơ hội/tài nguyên tiến triển. Quá nhiều task/threads tạo oversubscription và backlog. Với ASP.NET Core không dùng Task.Run mặc định cho I/O async, cũng không dùng .Result để giả đồng bộ. Bounded queue giới hạn cả backlog tốt hơn tạo một triệu task chỉ chờ gate.
