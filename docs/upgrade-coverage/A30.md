## Vị trí yêu cầu chung và nội dung giữ lại

- [Bản chất và vai trò](https://client-ifz4.vercel.app/#/read/efcore-migrations#identity): Migration là mô tả có phiên bản cho thay đổi schema database dựa trên model EF Core. LINQ to Entities là cách gọi thường dùng cho truy vấn LINQ được ORM dịch sang truy vấn database. Schema migration và truy vấn dữ liệu là hai nhiệm vụ khác nhau..
- [Nó giải quyết vấn đề gì?](https://client-ifz4.vercel.app/#/read/efcore-migrations#problem): Sửa class C# không tự thêm cột vào database đã tồn tại. Nếu mọi người tự chạy SQL bằng tay và không lưu lịch sử, các môi trường dễ lệch nhau. Migration lưu thay đổi có thứ tự trong source control để nhóm xem xét và áp dụng nhất quán..
- [Tại sao nên dùng nó?](https://client-ifz4.vercel.app/#/read/efcore-migrations#benefits): Thay đổi schema có thể review cùng code và dựng môi trường mới theo lịch sử đã lưu. EF hỗ trợ sinh script để xem trước; LINQ giữ truy vấn gần kiểu dữ liệu. Migration không tự bảo đảm không mất dữ liệu: rename bị hiểu thành drop/add vẫn cần sửa thủ công..
- [Giới hạn và điều kiện áp dụng](https://client-ifz4.vercel.app/#/read/efcore-migrations#limits): Ví dụ dùng SQLite lưu trong file school.db và quản lý schema bằng EF Core Migrations. Tạo migration, xem SQL rồi áp dụng vào database local mới trước khi chạy truy vấn. Không gọi EnsureCreated trong luồng này. Rollback schema không phục hồi nội dung đã xóa..
- [Cơ chế hoạt động cốt lõi](https://client-ifz4.vercel.app/#/read/efcore-migrations#mechanism): Khi add migration, EF so model hiện tại với model snapshot của lần migration trước, không phải tự diff toàn bộ database đang chạy. File migration có Up/Down; database lưu lịch sử migration đã áp dụng. Khi query thực thi, provider dịch biểu thức sang SQL; ToListAsync materialize dữ liệu, còn SaveChangesAsync ghi thay đổi đang được track..
- [Các khái niệm cốt lõi](https://client-ifz4.vercel.app/#/read/efcore-migrations#concepts): Migration, Tracking, Materialization.
- [Tương tác với thành phần khác](https://client-ifz4.vercel.app/#/read/efcore-migrations#integration): Deployment có thể dùng script đã review hoặc migration bundle. Package provider, EF Design và dotnet-ef cần major tương thích. Migration nên phối hợp chiến lược rollout app/schema: thêm cột tương thích trước, chuyển dữ liệu, rồi mới bỏ cấu trúc cũ khi phù hợp..
- [Ví dụ mở đầu và cách chạy](https://client-ifz4.vercel.app/#/read/efcore-migrations#hello): tài liệu cụ thể ở cuối bài.
- [Cấu trúc thư mục & cấu hình](https://client-ifz4.vercel.app/#/read/efcore-migrations#structure): Bố cục chính xác của từng ví dụ được liệt kê trong khối file của ví dụ đó. Đặt mỗi mẫu trong thư mục trống riêng; xem Hướng dẫn chạy chung để tạo Console, hiểu bin/obj và debug. Project nhiều file hoặc lab có nút tải đầy đủ và lệnh chạy riêng..
- [Debug & log lỗi](https://client-ifz4.vercel.app/#/read/efcore-migrations#debug): Dùng dotnet ef migrations list và kiểm tra connection/environment của startup project. Đọc Up/Down và SQL sinh bằng migrations script trước khi áp dụng. Với lỗi dịch LINQ, cô lập phần query không hỗ trợ; với query chậm, xem SQL và execution plan thay vì chỉ nhìn C#..
- [Tài liệu & cộng đồng](https://client-ifz4.vercel.app/#/read/efcore-migrations#resources): tài liệu cụ thể ở cuối bài.

## [Nền tảng junior cần giải thích được](https://client-ifz4.vercel.app/#/read/efcore-migrations#junior)

Migration quản lý schema bằng Up/Down, model snapshot và bảng history của database. CLI so model hiện tại với snapshot trước, không tự diff schema đang chạy. IDesignTimeDbContextFactory tạo context cho tool khi cách khởi tạo app phức tạp; không yêu cầu mọi app thêm constructor rỗng.

Luồng bài này dùng SQLite file school.db và migrations: add, script, review rồi update local mới. Không gọi EnsureCreated trong luồng này. Sau InitialCreate, thêm Email vào Student, add AddEmail và update; hàng An đã lưu vẫn tồn tại với default/migration được review. Truy vấn chung và tracking xem bài EF Core.

## [Đào sâu middle và các đánh đổi](https://client-ifz4.vercel.app/#/read/efcore-migrations#middle)

Rename có thể bị scaffold thành drop/add, cần sửa migration và đọc SQL để giữ dữ liệu. Down không khôi phục giá trị đã bị xóa; rollback schema không là backup dữ liệu. Deployment nên dùng script/bundle đã review và schema rollout tương thích nhiều app version, không mọi instance tự chạy update khi khởi động.

## Ví dụ và kiểm chứng

- [Cơ chế tối thiểu](https://client-ifz4.vercel.app/#/read/efcore-migrations#hello): **chỉ biên dịch**. Kỳ vọng: 0 khi school.db vừa được tạo và chưa có sinh viên.. Giải thích: SQLite file và migrations; không gọi EnsureCreated. Xem ví dụ MigrationLab để kiểm chứng hai lần thay schema. CLI tạo migration từ model và snapshot; migrations script hiển thị SQL để xem trước. database update áp dụng migration vào school.db local. Program truy vấn COUNT sau khi schema đã tồn tại.
  Bằng chứng: [upgrade-example-results.json](../upgrade-example-results.json), khóa `efcore-migrations/first`.
- [Hai migration với dữ liệu giữ nguyên](https://client-ifz4.vercel.app/#/read/efcore-migrations#variations): **lab dùng chung**. Kỳ vọng: Sau InitialCreate: students:1, name:An. Sau thêm Email và AddEmail: vẫn students:1, name:An; query cột Email hoạt động.. Giải thích: Project có design-time factory. Checker tạo một bản sao thư mục sạch, sinh migration, lưu An, sửa model thêm Email, sinh migration thứ hai, update rồi kiểm tra schema/dữ liệu.
  Bằng chứng: [upgrade-example-results.json](../upgrade-example-results.json), khóa `efcore-migrations/migration-evolution`; [lab report](../upgrade-lab-results.json), Two real EF migrations preserve An and add Email.
